# Codebase Concerns

**Analysis Date:** 2026-03-07

## Tech Debt

**Unmodified Scaffold — No Application Code:**
- Issue: The entire codebase is an unmodified `create-next-app` scaffold. `app/page.tsx` still contains the default placeholder content ("To get started, edit the page.tsx file.") with links to Vercel templates and Next.js docs. No actual application logic, components, routes, or business logic exist yet.
- Files: `app/page.tsx`, `app/layout.tsx`
- Impact: Nothing in the repo represents the intended product. All future work starts from scratch on top of a boilerplate shell.
- Fix approach: Replace `app/page.tsx` with actual application content. Update `app/layout.tsx` metadata (title, description) from the generated defaults.

**Default Metadata Never Updated:**
- Issue: `app/layout.tsx` exports `metadata` with `title: "Create Next App"` and `description: "Generated by create next app"`. These are the scaffold defaults and have not been customized.
- Files: `app/layout.tsx` (lines 15-18)
- Impact: SEO and browser tab title reflect the boilerplate generator, not the actual project.
- Fix approach: Set `title` and `description` to match the real application name and purpose.

**Empty Next.js Config:**
- Issue: `next.config.ts` contains no configuration — only the scaffolded empty object `const nextConfig: NextConfig = { /* config options here */ }`. No image domains, redirects, headers, environment variable exposure, or bundle optimizations are configured.
- Files: `next.config.ts`
- Impact: Any features requiring config (remote images, CSP headers, i18n, custom rewrites) will fail silently or require emergency config changes at the time of need.
- Fix approach: Populate as features are added. At minimum, configure `headers()` for Content-Security-Policy before going to production.

**No Lockfile Committed:**
- Issue: No `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, or `bun.lockb` is present in the repository root. `node_modules` exists locally but the lockfile that pins exact dependency versions is absent.
- Files: root directory
- Impact: Dependency resolution is non-deterministic. CI builds, collaborator installs, and deployments may resolve different versions than the developer's environment, causing hard-to-reproduce bugs.
- Fix approach: Run `npm install` (or the relevant package manager) and commit the generated lockfile immediately.

**Pinned Dependency Versions May Be Outdated:**
- Issue: `next` is pinned to `16.1.6` and `react` / `react-dom` to `19.2.3`. Without a lockfile these exact pinned strings are the only version control. `next` 16 is a pre-release / non-standard version identifier relative to the public Next.js versioning scheme — this may indicate an experimental or incorrectly specified version.
- Files: `package.json`
- Impact: If `next@16.1.6` does not exist on the registry or is a canary build, installs may fail or pull unexpected code.
- Fix approach: Verify the correct version identifier against the npm registry. Commit a lockfile to freeze the resolved tree.

## Security Considerations

**No Content Security Policy:**
- Risk: There are no HTTP security headers configured anywhere. No CSP, no `X-Frame-Options`, no `X-Content-Type-Options`, no `Referrer-Policy`.
- Files: `next.config.ts`
- Current mitigation: None.
- Recommendations: Add a `headers()` export to `next.config.ts` that sets at minimum `Content-Security-Policy`, `X-Frame-Options: DENY`, and `X-Content-Type-Options: nosniff`. Next.js makes this straightforward via the `headers` config key.

**External Links Without `rel="noopener noreferrer"` Audit:**
- Risk: `app/page.tsx` contains `<a>` tags pointing to external domains with `target="_blank"`. The scaffold correctly includes `rel="noopener noreferrer"` on these specific links, but there is no enforced lint rule preventing future external links from omitting this attribute.
- Files: `app/page.tsx` (lines 42-43, 55-56)
- Current mitigation: The scaffold-generated links happen to be correct.
- Recommendations: Confirm the ESLint rule `jsx-a11y/anchor-is-valid` or `react/jsx-no-target-blank` is active in `eslint.config.mjs` to enforce this automatically going forward.

**No Authentication or Authorization Layer:**
- Risk: The application has no auth whatsoever. If routes or API endpoints are added without a pre-existing auth strategy, they will be publicly accessible by default.
- Files: N/A — feature is absent
- Current mitigation: No sensitive routes or API endpoints exist yet.
- Recommendations: Decide on an auth strategy (NextAuth.js, Clerk, Supabase Auth, etc.) and add middleware protection before any protected routes are created.

## Performance Bottlenecks

**No Performance Budgets or Bundle Analysis:**
- Problem: There is no bundle analyzer configured and no size budgets set.
- Files: `next.config.ts`, `package.json`
- Cause: Default scaffold includes neither.
- Improvement path: Add `@next/bundle-analyzer` as a dev dependency and wrap `nextConfig` with it to catch bundle size regressions early.

**Google Fonts Loaded via `next/font/google`:**
- Problem: `layout.tsx` loads two Geist font families (Geist Sans, Geist Mono) from Google Fonts on every page. While `next/font` self-hosts at build time, the font loading still adds to the critical render path if not subsetted appropriately.
- Files: `app/layout.tsx` (lines 5-13)
- Cause: Default scaffold behavior.
- Improvement path: Confirm `display: 'swap'` is set (it is the default) and only include font weights actually used by the application.

## Fragile Areas

**Font Variable Classes Injected in Body Without Fallback Strategy:**
- Files: `app/layout.tsx` (line 29)
- Why fragile: The body element applies `${geistSans.variable} ${geistMono.variable}` CSS variables. If the font imports fail at build time (e.g., network issue, font name change), the build will error with no graceful fallback.
- Safe modification: Add a system-font fallback stack in `globals.css` alongside the CSS variable usage so the UI degrades gracefully.
- Test coverage: No tests exist.

**`globals.css` Declares `font-family: Arial, Helvetica, sans-serif` on `body` While Layout Uses CSS Variables:**
- Files: `app/globals.css` (line 25), `app/layout.tsx` (line 29)
- Why fragile: `globals.css` sets `font-family: Arial, Helvetica, sans-serif` directly on `body`, but `layout.tsx` applies Geist font via CSS variable classes. The Tailwind `font-sans` utility references `--font-sans` (the Geist variable). The hardcoded `Arial` declaration in `globals.css` is overridden by Tailwind utilities that apply `--font-geist-sans`, but the redundant conflicting declaration creates confusion about which font actually renders.
- Safe modification: Remove the hardcoded `font-family` rule from `globals.css` body selector and rely solely on the Tailwind `font-sans` / CSS variable system.
- Test coverage: No visual regression tests exist.
